The Aegra CLI manages project creation, development servers, and Compose deployments. `aegra dev`, `aegra up`, and `aegra down` run `docker compose` or `podman compose`. With `AEGRA_CONTAINER_RUNTIME` unset, each command picks the runtime as described below. Set the variable to `docker` or `podman` to choose directly.

## Install

```bash
pip install aegra-cli
```

<Warning>
  Install `aegra-cli` directly — not the `aegra` meta-package on PyPI.
</Warning>

## Commands

### `aegra init`

Create a new Aegra project interactively.

```bash
aegra init              # Prompts for location, template, and name
aegra init ./my-agent   # Create at path (still prompts for template)
```

Generates the project structure including `aegra.json`, `Dockerfile`, `docker-compose.yml`, `.env.example`, and a starter graph based on the selected template.

**Templates:**
- **simple-chatbot** — Basic conversational agent
- **react-agent** — ReAct agent with tool use

### `aegra dev`

Start the development server with hot reload and automatic PostgreSQL.

```bash
aegra dev
```

What it does:
1. Starts PostgreSQL with Compose. When `AEGRA_CONTAINER_RUNTIME` is unset, this prefers a running Docker daemon, then Podman if it is installed, then Docker if it is installed but stopped. Set the variable to `docker` or `podman` to choose directly.
2. Loads your `.env` file
3. Applies database migrations automatically
4. Runs uvicorn with `--reload` by default

| Option | Default | Description |
|--------|---------|-------------|
| `--host` | `127.0.0.1` | Host to bind to |
| `--port` | `2026` | Port to bind to |
| `--config` / `-c` | Auto-detected | Path to `aegra.json` |
| `--env-file` / `-e` | `.env` | Path to `.env` file |
| `--file` / `-f` | Auto-detected | Path to `docker-compose.yml` |
| `--no-db-check` | — | Skip database readiness check |
| `--no-reload` | — | Disable auto-reload |
| `--debug-port` | — | When set, run the server under `debugpy` and listen on this port (enables remote debugging) |
| `--wait-for-client` | `false` | When used with `--debug-port`, `debugpy` will wait for a debugger client to attach before starting the app |
| `--debug-host` | - | Host for the debugger to bind to (defaults to loopback). Binding to a non-loopback address is unsafe. |

### `aegra serve`

Start the production server without Docker. You must provide a running database.

```bash
aegra serve
```

What it does:
1. Loads your `.env` file
2. Replaces itself with uvicorn in production mode (no reload), so as a container's PID 1 the server receives `SIGTERM` directly and drains in-flight runs; on Windows, which has no exec, uvicorn runs as a child process
3. Applies database migrations automatically
4. Connects to the database configured via `DATABASE_URL` or `POSTGRES_*` variables

| Option | Default | Description |
|--------|---------|-------------|
| `--host` | `0.0.0.0` | Host to bind to |
| `--port` | From env or `2026` | Port to bind to |
| `--config` / `-c` | Auto-detected | Path to `aegra.json` |

Use `aegra serve` for:
- PaaS platforms (Railway, Render, Fly.io)
- Inside Docker containers (generated `Dockerfile` uses this as CMD)
- Bare metal / VM with external PostgreSQL
- Kubernetes pod specs

### `aegra up`

Build and start all Compose services (PostgreSQL + app). When `AEGRA_CONTAINER_RUNTIME` is unset, this uses a running Docker daemon, then Podman if it is installed, then Docker if it is installed but stopped. Set the variable to `docker` or `podman` to choose directly.

```bash
aegra up
```

| Option | Default | Description |
|--------|---------|-------------|
| `--build` / `--no-build` | Build on | Build images before starting |
| `--file` / `-f` | Auto-detected | Path to compose file |
| `SERVICE...` | All | Specific services to start |

### `aegra down`

Stop Compose services.

With `AEGRA_CONTAINER_RUNTIME` set to `docker` or `podman`, this uses only that runtime. If it is not running, `aegra down` tries to start it before running `compose down`, and exits non-zero if it cannot.

With the variable unset, this checks each installed runtime for containers from the Compose file, then runs `compose down` on every runtime that has them:

- A runtime whose status check exits non-zero counts as not running, whatever the cause, including a permission error. It is skipped, so its containers stay until that runtime can be reached and `aegra down` is run again, and `aegra down` can still exit successfully after stopping another runtime.
- Stopped containers are included when `compose ps --all` succeeds. If it fails, the check falls back to `compose ps`, which only sees running containers. A runtime with running containers still counts as an owner, so `aegra down` can exit successfully. A runtime with none counts as a failed check.
- If a runtime's status check times out, or its container listing or Podman Compose check fails or times out, `aegra down` stops the owners it can and exits non-zero. If it has no owner it can stop, it stops nothing. When the failure was a status check or listing, set the variable to choose a runtime.
- If every check finishes and no containers are found, it uses the same auto-detect order as `aegra up`. That order can select a skipped runtime that is not running. `aegra down` then tries to start it and runs `compose down` there, which removes its containers for this file, and its volumes with `--volumes`.

```bash
aegra down              # Stop containers
aegra down --volumes    # Stop and remove data volumes
```

### `aegra version`

Show version information.

```bash
aegra version
```

## When to use each command

| Scenario | Command |
|----------|---------|
| Local development | `aegra dev` |
| Self-hosted Docker production | `aegra up` |
| PaaS deployment (Railway, Render) | `aegra serve` |
| Kubernetes | `aegra serve` (in pod spec) |
| Inside a Docker container | `aegra serve` (as CMD) |
